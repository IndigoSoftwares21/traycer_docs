Traycer gives your application a wallet on Bitcoin, Ethereum, BSC, or Tron for every user you have, without you touching a private key, running a node, or building an indexer.

Everything is addressed by an identifier **you** choose — your user ID, order number, account reference. Traycer stores the mapping; you store nothing of ours.

```bash Create a wallet for user 8842
curl -X POST https://traycercoinsbe-production.up.railway.app/api/v1/http/wallets \
  -H "x-api-key: $TRAYCER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "walletReference": "user_8842", "network": "tron" }'
```

## How it fits together

<Steps>
  <Step title="Create a wallet" icon="plus">
    `POST /wallets` with your own `walletReference` returns an address on the network you picked. It is live immediately.
  </Step>
  <Step title="Funds arrive" icon="arrow-down">
    A background poller watches the chain. When it sees a transfer to one of your addresses it records the transaction and fires a `transaction.deposit` webhook.
  </Step>
  <Step title="Quote before you send" icon="calculator">
    `POST /transfers/quote` estimates the network fee and tells you whether the wallet can actually cover it. Token transfers need native currency for gas — this is where you find out.
  </Step>
  <Step title="Send" icon="paper-plane">
    `POST /transfers` signs and broadcasts. Pass an `Idempotency-Key` so a retry can never send twice.
  </Step>
  <Step title="Reconcile" icon="list-check">
    `GET /transactions` is the source of truth. Webhooks are a fast path, not a guarantee.
  </Step>
</Steps>

## Things worth knowing up front

<AccordionGroup>
  <Accordion title="You choose the identifiers" icon="fingerprint">
    `walletReference` is yours — `user_8842`, `order_10023`, whatever your system already calls the thing. It must be unique within your organization and may contain only letters, digits, underscores, and hyphens. Every wallet endpoint is addressed by it, so you never persist a Traycer ID.
  </Accordion>

  <Accordion title="Token transfers need native currency for gas" icon="gas-pump">
    A wallet holding 500 USDT and 0 TRX **cannot send USDT**. The fee is paid in TRX, and there is none. This is the single most common integration surprise, and [`POST /transfers/quote`](/api-reference/transfers/quote-transfer) exists to catch it before you broadcast. See [Networks and assets](/guides/networks-and-assets).
  </Accordion>

  <Accordion title="Your API key can move money" icon="key">
    The key in `x-api-key` is a bearer credential — anyone holding it can send funds from your wallets. Keep it server-side, never in a browser bundle or mobile app, and scope it `read` wherever writing is not needed. See [Authentication](/guides/authentication).
  </Accordion>

  <Accordion title="Webhooks are delivered once, with no retry" icon="bell">
    A delivery is attempted a single time and the outcome is logged either way. If your endpoint is down for thirty seconds you have missed those events permanently. Treat webhooks as the fast path and reconcile against [`GET /transactions`](/api-reference/transactions/list-transactions) for anything that matters. See [Webhooks](/guides/webhooks).
  </Accordion>

  <Accordion title="A 201 on a transfer means broadcast, not confirmed" icon="triangle-exclamation">
    The transaction was accepted by the network. It can still fail, and it can never be reversed. Confirmation arrives via the `transaction.withdrawal` webhook or [`GET /transfers/{txHash}`](/api-reference/transfers/get-transfer).
  </Accordion>
</AccordionGroup>

## Base URL

```bash
https://traycercoinsbe-production.up.railway.app/api/v1/http
```

<Note>
  Every path in these docs is relative to this base. The `v1` segment comes from the server's `API_VERSION` setting and defaults to `v1`.
</Note>
